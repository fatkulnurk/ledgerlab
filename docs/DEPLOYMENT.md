# Deployment

Deploy to **at least one** of Render / AWS / GCP / Azure, over HTTPS, with health
checks and a managed database. Then, for bonus marks, put **Cloudflare** in front
on a **real TLD**.

## Recommended path: Render (fastest to a real URL)

The blueprint is committed at [`deployment/render.yaml`](../deployment/render.yaml).
It provisions:

| Resource                     | Type        | Notes                                               |
| ---------------------------- | ----------- | --------------------------------------------------- |
| `koiledgerlab-db`            | Postgres 16 | private network only (`ipAllowList: []`)            |
| `koiledgerlab-ledger-api`    | Docker web  | `numInstances: 2`, `/health`, pre-deploy migrations |
| `koiledgerlab-reporting-api` | Docker web  | `numInstances: 2`, `/health`                        |
| `koiledgerlab-web`           | Static site | SPA rewrite + security headers                      |

All resources are in **singapore** — Render's private network only spans one
region, so the database and the services must match.

### First deploy, step by step

1. **Merge the branch to `main`.** The Blueprint deploys from the repo's default
   branch.
2. In the Render Dashboard: **New → Blueprint → select `fatkulnurk/ledgerlab`**.
   (Or `render blueprint launch` with the Render CLI.)
3. Render prompts for the four `sync: false` values. Fill them in:

   | Key (service)                  | Value                                             |
   | ------------------------------ | ------------------------------------------------- |
   | `CORS_ORIGINS` (ledger-api)    | `https://koiledgerlab-web.onrender.com`           |
   | `CORS_ORIGINS` (reporting-api) | `https://koiledgerlab-web.onrender.com`           |
   | `VITE_LEDGER_API_URL` (web)    | `https://koiledgerlab-ledger-api.onrender.com`    |
   | `VITE_REPORTING_API_URL` (web) | `https://koiledgerlab-reporting-api.onrender.com` |

   > If a service name is already taken in your workspace, Render appends a
   > suffix and the URL changes. **Check the actual URLs in the dashboard** and
   > use those values instead.

   > `NODE_ENV=production` is baked into the images, so the ledger API **refuses
   > to boot** if `CORS_ORIGINS` is `*` or `INTERNAL_API_TOKEN` is missing. Fill
   > the values before the first deploy.

4. Wait for the pipeline: **build → `preDeployCommand` (migrations) → deploy**.
   Migrations run once per deploy, never on container boot.
5. Verify:

   ```bash
   curl -s https://koiledgerlab-ledger-api.onrender.com/health
   # {"status":"ok","service":"ledger-api",...,"repository":"postgres"}

   curl -s -o /dev/null -w '%{http_code}\n' -X POST \
     https://koiledgerlab-ledger-api.onrender.com/api/internal/postings
   # 401 — never 200

   curl -sI https://koiledgerlab-web.onrender.com | grep -i strict-transport-security
   # max-age=31536000; includeSubDomains; preload
   ```

6. Open the dashboard and record your first accounts and journal entry.

**Production starts empty** — no demo data is seeded. Seeding is local-only.

`INTERNAL_API_TOKEN` is generated by Render and shared to the reporting service
via `fromService`, so `/api/internal/*` stays service-to-service only.

### Cost and teardown

Compute is billed **per second**: 2 replicas × 2 API services (`0.5c-512mb`,
$7/mo each) plus Postgres `0.1c-256mb` ($6/mo) ≈ **$34/month**, i.e. about
**$1.12/day**. To stop the cost, **delete or suspend** the three services and the
database in the dashboard — leaving them running keeps billing.

### Keeping the blueprint valid

Run the validator after any edit to `render.yaml` (it catches schema errors such
as an unknown plan id before a sync):

```bash
render blueprints validate deployment/render.yaml
```

## Run the production stack locally (reproducible, no cloud account)

This is the same artifact Render deploys, exercised end to end:

```bash
pnpm db:up          # docker compose up -d db   (Postgres 16)
export DATABASE_URL=postgres://ledgerlab:ledgerlab@localhost:5432/ledgerlab
pnpm db:migrate     # applies packages/db/migrations/*.sql (idempotent)
pnpm db:seed        # demo data (idempotent)
pnpm docker:build   # builds ledger-api, reporting-api and web images
```

Run the images the way the platform would:

```bash
docker run --rm -p 4021:4021 \
  -e DATABASE_URL=postgres://ledgerlab:ledgerlab@host.docker.internal:5432/ledgerlab \
  -e INTERNAL_API_TOKEN=docker-token -e CORS_ORIGINS=https://app.example.com \
  ledgerlab/ledger-api
# GET /health -> {"repository":"postgres", ...}
```

Verified locally: `repository: postgres`, `/api/internal/postings` → `401`
without the token, HSTS present, and the reporting image returns a balanced
dashboard sourced from the ledger container over HTTP.

## Environment variables

| Variable                  | Service       | Required | Notes                                      |
| ------------------------- | ------------- | -------- | ------------------------------------------ |
| `DATABASE_URL`            | ledger-api    | prod     | Postgres/MySQL connection string           |
| `PORT`                    | both APIs     | platform | set by Render; the app binds it on 0.0.0.0 |
| `LEDGER_API_PORT`         | ledger-api    | no       | local dev override; default `4001`         |
| `REPORTING_API_PORT`      | reporting-api | no       | local dev override; default `4002`         |
| `LEDGER_API_URL`          | reporting-api | yes      | ledger base URL                            |
| `INTERNAL_API_TOKEN`      | both APIs     | prod     | guards `/api/internal/*`; required in prod |
| `CORS_ORIGINS`            | both APIs     | prod     | comma-separated; `*` refuses to boot       |
| `RATE_LIMIT_MAX`          | both APIs     | no       | default `120` requests per window          |
| `RATE_LIMIT_WINDOW_MS`    | both APIs     | no       | default `60000` ms                         |
| `DB_POOL_MAX`             | ledger-api    | no       | default `10` connections per replica       |
| `DB_IDLE_TIMEOUT_SECONDS` | ledger-api    | no       | default `30` s                             |
| `CLOSED_THROUGH`          | ledger-api    | no       | reject entries on/before this date         |
| `VITE_LEDGER_API_URL`     | web           | yes      | baked in at build time                     |
| `VITE_REPORTING_API_URL`  | web           | yes      | baked in at build time                     |

> The two `VITE_*` values are **build-time**, not runtime. Change the API host?
> Rebuild the dashboard.

## Health checks

Both APIs expose `GET /health` returning
`{ status, service, version, uptimeSeconds, repository }`. Point the platform's
health check at it and use it for zero-downtime rollout and rollback.

## Docker

```bash
# APIs (build from the repo root)
docker build -f deployment/Dockerfile.ledger-api    -t ledgerlab/ledger-api .
docker build -f deployment/Dockerfile.reporting-api -t ledgerlab/reporting-api .

# Dashboard (bake in the API URLs)
docker build -f deployment/Dockerfile.web \
  --build-arg VITE_LEDGER_API_URL=https://api.example.com \
  --build-arg VITE_REPORTING_API_URL=https://reports.example.com \
  -t ledgerlab/web .
```

## What "production-scale" means here (G4)

- [x] **Stateless** services — no local disk state; any replica can serve any request.
- [x] **≥2 replicas** — `numInstances: 2` on both API services in `render.yaml`.
- [x] **Managed database** with backups and a private network path (Render Postgres).
- [x] **Connection pooling** sized to the plan (`DB_POOL_MAX`, idle timeout); no connection-per-request.
- [x] **Graceful shutdown**: SIGTERM drains in-flight requests and closes the pool
      (already wired in both `src/index.ts` files).
- [x] **Health checks** gate the rollout; a failing replica is replaced.
- [x] **Migrations as a separate step**, never on container boot
      (`preDeployCommand` → `packages/db/migrate.mjs`).
- [ ] **Observability**: structured logs retained, an alert on 5xx and p95 latency.
- [x] **Reproducible**: one documented command (or a committed blueprint/IaC)
      recreates the environment — `render blueprint launch` + `pnpm docker:build`.

## Rollback and migrations

- Keep migrations backward compatible for one release (add columns, don't
  rename/drop in the same deploy).
- Roll back the app by redeploying the previous image — the DB must still work
  with it.
- Never roll back by reverting a migration in production unless you have
  verified it is lossless.
